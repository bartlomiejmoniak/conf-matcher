# Roadmap — decisions from the October 2026 brainstorm

Confgraph is moving from "static site + browser storage" to "static venue data + a small
user backend + community contribution". This note records what was decided and in which
order the pieces get their own spec. Each numbered item is a separate spec → plan → build.

## Direction

A mix of commons and product. The core venue facts stay open; revenue comes from
user-side convenience (sync, calendar feeds, collaboration), never from locking up the
data. The goal is eventually to earn more than the servers cost, not to maximise it.

## Sequence

1. **Accounts and sync** — [spec](2026-10-30-accounts-and-sync-design.md). Supabase,
   GitHub + Google sign-in, sync of watchlist, paper profile and tracked papers. Browser
   storage stays the default for anyone who does not sign in.
2. **Contribution pipeline.**
   - A browser extension the user switches on. It reads the conference page the user has open — no crawler.
   - Extraction is rules first, then an AI model for messy pages: on-device where the browser offers one (e.g. Chrome's built-in model), else server-side with a per-user cap. The output is always a proposed change that the user confirms.
   - Review mixes humans, AI checks and votes, weighted by reputation.
   - Reputation is seeded once, before a user's first contribution, from a linked ORCID iD (publications looked up in OpenAlex, which is CC0) and/or GitHub account history. After that only Confgraph's own reputation counts.
   - Contributor terms grant Confgraph a broad licence over submissions. They must exist before the extension ships.
   - Venue facts move into Postgres as the source of truth; `venues.json` and the public dump become generated outputs. The validate/quarantine rules move with them.
3. **Distribution.**
   - A partial public dump under ODbL: core facts only (venues, dates, host/workshop links).
   - A live API and an MCP server with keys, rate limits, a free tier and a paid commercial tier.
   - User reviews, reputation and edit history are never in the dump.
   - CORE, CCF and h5 rankings are displayed with attribution, but go into the dump or the API only with the publisher's permission. Ask CORE and CCF directly. h5 values are entered one at a time with a source link; Google Scholar is never bulk-scraped.
4. **Collaboration (premium).**
   - Shared watchlists and a submission board for a lab or co-author group.
   - A shared draft workspace: outline, notes, checklist and a link to Overleaf or Docs.
   - Real-time co-editing later, on an existing CRDT library (e.g. Yjs), if ever.
5. **Monetisation.**
   - Premium: a private calendar subscription URL, collaboration, alerts on extensions and CFP openings.
   - Ads remain an open alternative.
   - Heavy contributors earn time-limited free premium.

## Standing technical decisions

- **No graph database.**
  - At tens of thousands of venues and workshops, host/workshop links are a link table in Postgres.
  - A recursive query walks them in milliseconds.
  - Revisit only if traversals become deep and unpredictable at millions of edges.
- **Supabase over Firebase or self-run MySQL.**
  - Relational data suits teams and sharing, and row-level security lets the static frontend talk to the database directly.
  - It's plain Postgres underneath, so moving to dedicated hosting later is just moving a database.
- **Sign in with Apple is deferred.** It requires the paid Apple Developer Program ($99/year).
- **ORCID Public API is non-commercial only.**
  - Use ORCID for proving who someone is (OAuth sign-in or linking).
  - Use OpenAlex for publication data.
  - Becoming an ORCID member is the route if heavier ORCID use is ever needed.
- **Code licence (open question).** AGPL for the app code is the leading option.
